# Theme compilation and refresh

The application catalog declares the Sass entry point, generated inputs and final
CSS output for Waybar, Walker, SwayOSD and Wlogout. Walker receives a real
`themes/<theme>/style.css`, alongside its generated color partial. SwayOSD's
`style.scss` imports the `_colors.scss` partial generated by its application spec.

Normal configure renders and checks all source artifacts, copies each stylesheet
directory into private scratch space, overlays the newly rendered partials, and
runs `sassc` there. A missing compiler or invalid stylesheet stops application
before any theme output is installed. Only after all four compilations succeed
does the coordinator install source artifacts and compiled CSS together. CSS is
covered by the same journal, failure recovery and rollback as token files.

Dry-run starts no compiler and creates no scratch directory. It reports pending
compilations explicitly; it cannot claim compiler-level validation. Normal runs
recompile to detect changes in static SCSS too. Identical final content causes no
application refresh or wallpaper update.

Refresh handlers never compile or write CSS. SwayNC uses its native config/CSS
reload API, preserving the notification daemon. Refresh happens once per affected
handler after the transaction commits. Portal lifecycle is independent of theme
changes. A refresh error reports that files were committed and suggests `dotfiles
reload` or `dotfiles rollback`.

The real Arch tests compile all four styles for light and dark, repeat an unchanged
theme, and restore CSS through rollback. They also verify that failed compilation
does not install theme files and that declarative source remains unchanged.
